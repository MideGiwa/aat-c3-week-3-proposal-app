# AI Proposal Document Application

Turns discovery-call intake into a Claude-drafted proposal, lets a salesperson review/edit/regenerate it section by section, routes it through internal approval, generates a client-ready PDF, sends it, and keeps a central log of every proposal and what happened to it.

This implements Phases 0–9 of `implementation-plan.md` in the project: setup, intake, AI generation, section editing/regeneration, the approval workflow, PDF document generation, delivery, a frontend UI polish pass, a dedicated failure-mode testing pass, and a full UI/UX overhaul (branding, navigation, and review experience). Phase 10 (the submission deliverables) is next — see that doc for the full breakdown.

## Stack

- **Next.js 16** (App Router, TypeScript, Tailwind) — one deployable for frontend + API routes.
- **PostgreSQL in production, SQLite in local dev** via **Drizzle ORM** (`src/lib/db/schema.ts`, dispatches on `DATABASE_URL` — see `DATABASE.md`) — chosen over Prisma specifically because Prisma's engine binaries couldn't be downloaded in the sandbox this was built in; Drizzle is pure JS/TS and needs no native binary, which also tends to be friendlier on serverless hosts. Prisma remains an equally valid choice if you'd rather use it — the schema translates directly.
- **Anthropic SDK** (`src/lib/anthropic.ts`) — forces structured output via tool use, so section boundaries and the "needs input" signal are reliable rather than parsed out of free text.
- **pdfkit** (`src/lib/pdf.ts`) — chosen over printing HTML through a headless Chromium (the architecture doc's original suggestion) because shipping a real browser binary is a real headache on serverless hosts and needs no download here either; pdfkit is pure JS and "just works" wherever Node runs. Renders a small markdown subset (paragraphs, `- ` bullets, `**bold**`) since that's what the generation prompt asks Claude for.
- **Resend or n8n** for delivery (`src/lib/email.ts`) — a config-only switch (`EMAIL_PROVIDER=resend|n8n`), see below.
- Minimal placeholder auth (`src/lib/auth.ts`) — pick a seeded user, no password. Replace before this is anything but an internal project.

## Setup

```bash
npm install
cp .env.example .env.local   # fill in DATABASE_URL and ANTHROPIC_API_KEY (see note below if using Supabase)
npm run db:push              # create tables from src/lib/db/schema.ts
npm run seed                 # seed a salesperson + an approver user
npm run dev
```

Then open `http://localhost:3000`, sign in as one of the seeded users, and create a proposal from `/proposals/new`.

### If `db:push` fails with "Interactive prompts require a TTY terminal"

`drizzle-kit push` always shows an interactive confirmation summary before it applies anything — including on a brand-new, empty database with nothing to lose. In an ordinary terminal that's harmless (press enter to confirm), but in any context that isn't a real TTY — CI, a Docker build step, a non-interactive script, or the sandbox this app was built and tested in — that prompt has nothing to render to and the command aborts with `Interactive prompts require a TTY terminal`, **without creating any tables**. `npm run seed` will then fail too, but with a much less obvious error: `relation "users" does not exist` — a raw Postgres error that doesn't point back at the real cause (schema was never pushed).

If you hit either error, run `npm run db:push:force` instead (`drizzle-kit push --force`), which auto-approves and skips the prompt entirely, then re-run `npm run seed`. Use the plain `npm run db:push` day-to-day in a real terminal, since it's the one that still warns you before a genuinely destructive change (e.g. a column drop or rename); reach for `db:push:force` only when you know there's nothing to lose (first setup) or you're in a non-interactive context.

### A note if you're pointing this at Supabase

`DATABASE_URL` needs Supabase's **Postgres connection string** (Project Settings → Database → Connect → "ORMs" tab → Drizzle gives you the exact string, with a password placeholder to fill in) — Drizzle talks to Postgres directly over the wire protocol. The **project URL and publishable/anon key** (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`) are a different thing: they're for Supabase's client libraries (Auth, Storage, the JS/REST client), which this app doesn't use yet, and that key alone can't run schema migrations or read past Row Level Security. Both are documented in `.env.example`. If you'd rather this app used Supabase Auth (replacing the placeholder sign-in) or Supabase Storage (replacing the local-disk PDF storage below), that's a real option — say so and it can be the next phase — but it's a different, larger change than "add the connection string," so it's called out here rather than assumed.

**If your database password has special characters, percent-encode it before it goes in the URL.** A password containing `@`, `%`, `?`, `#`, `/`, `:`, or whitespace will silently corrupt the connection string if pasted in raw — an unescaped `@` gets read as the userinfo/host separator (so the real host is lost), an unescaped `?` gets read as the start of the query string (so the rest of the password and the host vanish into it), and a bare `%` isn't valid percent-encoding on its own. The failure this produces (`getaddrinfo ENOTFOUND <garbage>`, or a wrong/truncated password) looks nothing like a normal authentication error and is easy to mistake for a code bug. Fix it by running `encodeURIComponent("your-password")` in a Node/browser console and using that output in the URL instead of the raw password — or simpler, reset the database password in Supabase to one without special characters.

## What's implemented

- **Intake** (`/proposals/new`, `POST /api/proposals`) — validates required fields from `intake-form-fields.md` before anything is sent to Claude.
- **Generation** (`POST /api/proposals/:id/generate`) — drafts all six sections from `proposal-template.md` in one call; any section Claude can't responsibly write is flagged `[NEEDS INPUT: ...]` rather than guessing, and that flag blocks submission for review.
- **Supporting material** (`POST /api/proposals/:id/attachments`) — uploaded `.txt`/`.md`/`.csv` files are extracted and passed into generation as context. Other file types are stored but not yet extracted (an intentional gap — see below).
- **Section editing & regeneration** (`PATCH .../sections/:sectionId`, `POST .../sections/:sectionId/regenerate`) — every edit or regeneration writes a new `section_versions` row rather than overwriting, so history is never lost and unrelated sections are untouched. The section it came from is recorded via `sections.currentVersionId`, so a generated document can point at the exact versions it was built from.
- **Approval workflow** (`POST /api/proposals/:id/submit`, `POST /api/proposals/:id/decision`) — an explicit status state machine, enforced server-side: only an `approver` can decide, and nothing can move past `pending_review` without it.
- **Document generation** (`POST /api/proposals/:id/documents`, `GET /api/documents/:documentId/download`) — renders a PDF from the current section content. The download route deliberately doesn't require sign-in, since it's the link a client (with no account here) gets by email — security is an unguessable UUID rather than auth, a known simplification (no expiry/revocation).
- **Delivery** (`POST /api/proposals/:id/send`) — only callable once `approved` (or retrying a `send_failed`); always regenerates the PDF from current content first, so a late edit can never result in a stale document being sent; composes the email from `client-email-template.md`; sends via whichever provider `EMAIL_PROVIDER` names.
  - **Resend** (default): a direct API call. Needs `RESEND_API_KEY` and `EMAIL_FROM`.
  - **n8n**: this app POSTs `{to, subject, html, text, proposalLink, clientName, companyName, salespersonName}` to `N8N_WEBHOOK_URL` (with an optional `x-webhook-secret` header) and treats any `2xx` as success; an n8n workflow behind that webhook does the actual sending. A minimal workflow: a **Webhook** trigger node, then any send node (Gmail/SMTP/Resend/whatever the team already uses in n8n) mapped from the webhook body's `to`/`subject`/`html` fields, then a **Respond to Webhook** node returning 200.
  - Switching providers is a one-line env change (`EMAIL_PROVIDER=resend` or `n8n`) — no code or redeploy logic depends on which is active.
- **Central log** (`/proposals`, the `events` table) — every transition and failure is recorded with a specific reason, not just a status column.
- **Failure handling** — generation, document-build, and send failures are all classified, retried once where it makes sense (generation), and surfaced on the proposal with the actual reason rather than a silent stuck state; a `send_failed` or `document_failed` proposal can be retried directly from the same action that failed. A dedicated Phase 8 pass forced all three failure modes for real against a running server and found (and fixed) a genuine stuck-state bug: a proposal that failed document generation had no way back to `approved` even after a successful retry — see `implementation-plan.md`'s Phase 8 for the full writeup.
- **Frontend polish (Phase 7)** — status is now shown as the same colored badge on both the dashboard and the proposal detail page, driven by one shared `STATUS_LABEL`/`STATUS_STYLES` map in `src/lib/proposal-fields.ts` so the two screens can't drift apart again; every mutating action (generate, save, regenerate, upload, PDF generation, submit, approve/request changes/reject, send) now shows a dismissing green success banner in addition to the existing red error banner; the Approve/Request changes/Reject buttons got the same per-action busy label the rest of the app already had; the dashboard table scrolls horizontally at narrow widths instead of squashing; and there's a visible keyboard-focus outline on every interactive element (`globals.css`), which nothing in the app defined before.
- **UI/UX overhaul (Phase 9)** — a full pass beyond Phase 7's functional polish: a single teal accent color replaces the all-black primary buttons app-wide, and the nav/login/browser-tab branding now reads "Koya Talent" (matching the sender identity already used in the PDF and email templates) instead of the generic project name. The proposal detail page gained a `StatusStepper` (Draft → Review → Approved → Sent) so progress reads at a glance, a section-completion progress bar, and a `MarkdownLite` renderer that shows bold/bullets/`[NEEDS INPUT: ...]` highlighting instead of a plain disabled `<textarea>` once a proposal is no longer editable (approvers now read a formatted document, not raw text in a form field). The Document card embeds the latest PDF in an inline `<iframe>` preview instead of only a download link. The dashboard gained status filter tabs, a client/company search box, and quick stat counts — both built as plain `<Link>`/`<form method="GET">` query-string navigation, no client JS needed. "Request changes" no longer uses the browser's native `prompt()`; it expands into an inline textarea matching the rest of the app.

## Known gaps (tracked, not accidental)

- **Attachment text extraction** only covers plain-text formats today; PDF/DOCX extraction is a scoped follow-up.
- **The document download link has no expiry or access control** beyond an unguessable id — reasonable for this stage, not for a production proposal tool handling sensitive pricing.
- **Auth is a placeholder.** Fine for an internal course project; not fine beyond that.

## Verifying this build

Phases 0–4 were smoke-tested against a real local Postgres instance (schema push, seeding, intake validation, AI-generation failure classification, role-enforced approvals, file upload). Phase 5–6 additions were verified the same way: a proposal was pushed through submit → approve → PDF generation, and the downloaded file was confirmed to be a real, readable, correctly-wrapped 2-page PDF with markdown bullets/bold rendered correctly. The email dispatcher was exercised directly for all three real paths it can take — Resend with no key (fails cleanly, classified, no crash), Resend with an invalid key (makes a real call to Resend's API, surfaces their actual rejection), and n8n against a live test webhook (payload received and shaped correctly) — and then the full `/send` route was run end to end against a running server: first failing (no Resend key configured) and flipping the proposal to `send_failed` with the reason logged, then retried against an n8n-configured instance, which regenerated the PDF fresh, delivered successfully, and flipped the proposal to `sent` with the provider and document id recorded in the audit log.

Phase 8's failure-mode pass forced all three real failure paths against a running server: a missing `ANTHROPIC_API_KEY` (generation), a forced `pdfkit` crash (document build), and both a missing `RESEND_API_KEY` and an unreachable n8n webhook (send) — each confirmed to produce the right status, event, and plain-language `lastError`, with no stack traces ever surfacing to the dashboard. Phase 9's UI overhaul was checked the same way rather than just by reading the component code: a proposal was pushed through draft → submit → approve → PDF generation with rendered HTML fetched directly, confirming the stepper reaches the right step at each stage, the section-completion count is accurate, the approver's read-only view renders bold/bullets as real HTML (not a disabled textarea), the inline PDF preview points at the latest document, and the dashboard's filter tabs and search return the right proposals (including the correct empty-state message when a filter or search matches nothing). `npm run build` and `npm run lint` both pass clean throughout.
