# Implementation Plan: AI Proposal Document Application

This breaks the architecture in `architecture.md` into buildable phases and concrete tasks. Phases are ordered by dependency, not by priority — a phase generally can't start meaningfully until the one before it has working (even if rough) output, since each phase builds on data or endpoints the previous one created. Within a phase, frontend and backend tasks can usually run in parallel once the API contract for that phase is settled.

**Status: Phases 0–9 are built and smoke-tested in `app/`. Phase 10 remains.** Two implementation choices deviated from the original plan, both for portability/sandbox reasons rather than the plan being wrong — see `app/README.md`'s "Stack" section for the full rationale: **Drizzle ORM** instead of Prisma (Prisma's engine binaries couldn't be downloaded in the build sandbox), and **pdfkit** instead of headless-Chromium/Puppeteer for PDF rendering (no browser binary to ship or download). Delivery also gained a capability not in the original plan: **Resend and n8n are both wired up**, switchable with one environment variable (`EMAIL_PROVIDER`), so the team can route outbound email through an n8n workflow instead of a direct API call if that fits how they already work.

## Issues found & fixed during verification

This section records real bugs and misconfigurations found by actually running the app end to end, rather than just reading the code — in the spirit of Phase 8 below.

**1. `npm run db:push` silently applies nothing in a non-interactive shell, and the resulting `seed` failure doesn't explain why.** `drizzle-kit push` always renders an interactive confirmation summary before applying anything, even on a brand-new database with zero risk of data loss. That's harmless in a normal terminal (press enter), but in any non-interactive context — CI, a Docker build step, or the sandbox this app is built/tested in — there's no TTY to render to, so the command aborts with `Interactive prompts require a TTY terminal` and creates no tables. Running `npm run seed` next then fails with a much less helpful error, a raw Postgres exception: `relation "users" does not exist` — which looks like a seed-script bug but is actually just "the schema was never pushed." *Fix (code, committed):* added an `npm run db:push:force` script (`drizzle-kit push --force`, auto-approves and skips the prompt) and documented the whole failure mode and its fix directly in `app/README.md`'s Setup section, so the confusing second-order error points back to the real cause instead of being a dead end. `db:push` itself is left as-is for normal interactive use, since it's the one that still warns before a genuinely destructive change later (a column drop/rename).

**2. `seed.ts` reported "Seeded 2 users" even when it inserted zero.** The script uses `onConflictDoNothing`, correctly, so re-running it is safe — but the final `console.log` unconditionally printed the total count of users *attempted*, not the count actually inserted, regardless of how many were skipped as already-existing. Re-running `npm run seed` against an already-seeded database printed "Seeded 2 users." when it had in fact created none. *Fix (code, committed):* each insert now captures its `.returning()` result to know whether a row was actually created, and the script reports created vs. skipped counts separately (e.g. `Seed complete: 0 user(s) created, 2 already existed (skipped).`). Verified against three cases: an empty table (2 created, 0 skipped), a fully-seeded table (0 created, 2 skipped), and a partially-seeded table (1 created, 1 skipped) — all report correctly now. `npx tsc --noEmit` and `npm run lint` both still pass clean.

**3. A malformed `DATABASE_URL` produced `getaddrinfo ENOTFOUND base` instead of a real connection error.** After pointing the app at a real Supabase project, every DB-backed route (e.g. `GET /api/auth/login`) failed with `Error: getaddrinfo ENOTFOUND base` — a hostname that appears nowhere in the actual Supabase connection string, which made it look like a code bug. The real value in `app/.env` was:
  ```
  DATABASE_URL="`postgresql://postgres.<ref>:[YOUR-PASSWORD]@aws-1-eu-west-1.pooler.supabase.com:6543/postgres?pgbouncer=true"
  ```
  A stray backtick sits right after the opening `"`, before `postgresql://`. Confirmed by reproducing the exact parse with `pg-connection-string` (the library `pg`/Drizzle use to parse `DATABASE_URL`): because the value no longer starts with a recognized `postgres://`/`postgresql://` prefix, the parser falls back to a completely different (libpq keyword=value) parsing path, which mis-derives `host: "base"` from the garbled string — hence the bizarre, seemingly-unrelated hostname in the error. Removing the stray backtick alone makes the same library parse `host`/`port`/`user`/`database` correctly. Independently, `[YOUR-PASSWORD]` — the literal placeholder from Supabase's template — had never been replaced with a real password either.

**4. After filling in the real password, `seed` still failed — the backtick was still there, and the password itself needed URL-encoding.** Two compounding issues, both confirmed with the same `pg-connection-string` reproduction used for #3:
  - The stray backtick from #3 was still present in the line — only `[YOUR-PASSWORD]` had been swapped for the real password in place, so the string was still fundamentally unparseable as a URL and would still misresolve to `host: "base"`.
  - The real database password itself contains characters that are structurally special in a URL — an `@`, a `%`, and a `?` — none of them percent-encoded. Reproducing the parse showed exactly why this corrupts the connection even with the backtick removed: the parser takes the *first* unescaped `@` as the userinfo/host separator, so everything after the password's own `@` (including the real hostname) gets misread as part of the host, yielding a garbage `host` value and a truncated, wrong password. A literal `%` not followed by two hex digits and a literal `?` (which structurally begins a URL's query string) compound the corruption further.
  - *Fix:* percent-encode the password with `encodeURIComponent(...)` before placing it in the connection string (verified this round-trips correctly — the parsed-out password matches the real one exactly once encoded), and remove the stray backtick.
  - **General takeaway for `app/README.md`'s Supabase note:** any database password containing `@`, `%`, `?`, `#`, `/`, `:`, or whitespace must be percent-encoded before it goes into `DATABASE_URL` — otherwise the failure it produces looks nothing like a normal auth error and is easy to mistake for a code bug or a wrong password. Resetting the password to one without special characters is a simpler alternative if encoding by hand is error-prone.

**5. Once the connection string itself was correct, `seed` still failed with DNS errors — first `EAI_AGAIN`, then `ENOTFOUND db.<ref>.supabase.co` — both explained by the developer's network, not the app.** With the pooler URL fully fixed, the pooler hostname (`aws-1-eu-west-1.pooler.supabase.com`) still failed to resolve on the developer's machine (`EAI_AGAIN`, then a plain OS `nslookup` returned `Server failed`). The `nslookup` output showed the machine was on a mobile hotspot (DNS server `172.20.10.1`, the standard iOS Personal Hotspot gateway address) — the hotspot's own DNS resolver was failing to resolve that specific AWS-load-balancer-backed hostname, not a problem in the app. Switching `DATABASE_URL` to Supabase's **direct connection** hostname (`db.<ref>.supabase.co`) instead of the pooler then produced `ENOTFOUND` for *that* host — and this one is structural, not transient: looking it up shows `db.<ref>.supabase.co` has **only an IPv6 (AAAA) record, no IPv4 (A) record at all**, which is Supabase's documented behavior for direct connections. A mobile hotspot (and many other IPv4-only networks) cannot resolve or route to an IPv6-only host, so this specific combination — direct connection + IPv4-only network — can never work, retry or not.
  - **Fix (not a code change — a connection-target and networking fix):** use the **pooler** hostname (Transaction or Session mode, both under `*.pooler.supabase.com`), never the direct-connection hostname, on any network that might be IPv4-only (mobile hotspots especially) — the pooler is Supabase's IPv4-compatible option specifically for this reason. Separately, to fix the pooler hostname's own DNS resolution failure on the hotspot's resolver: set the Windows network adapter's DNS servers explicitly to a public resolver (8.8.8.8 / 1.1.1.1) instead of letting it inherit the hotspot's DNS, which routes around whatever is failing in the hotspot's own resolver.
  - This is an environment/networking issue outside the codebase, not something further code changes fix — recorded here because it's a real, repeatable trap (IPv4-only networks + Supabase's direct-connection hostname) that anyone on this project working from a mobile hotspot or a restrictive network is likely to hit.

  *Not fixed automatically (same guardrail as #3/#4):* `.env` and OS-level network settings are both outside what the remote file tools can change; reported back with the specific hostnames to use/avoid and the DNS-server workaround.

  **Status: connection confirmed working.** A later `npm run seed` run reached the real Supabase database and failed with a genuine Postgres error (`relation "users" does not exist`, code `42P01`) rather than any DNS/network error — proof the connection string, hostname, and network path are all correct now. That specific failure is #1 above (`db:push` was never run against this database, so the schema doesn't exist yet): the fix is `npm run db:push:force` followed by `npm run seed`, not anything further on the networking side.

## Phase 8 — Failure handling pass

Goal: deliberately verify that every failure mode is visible and debuggable, not just handled in theory.

- [x] Audit that all four risk points (generation, document build, approval, send) write to `events` on both success and failure with enough detail to reconstruct what happened. *(read every route in the chain directly. - [x] Confirm the dashboard surfaces the failure reason in plain language, not a raw stack trace or a silent stuck state. *(verified directly against rendered HTML, not just by reading the component code: every failure surfaces the exact classified string — e.g. `config: ANTHROPIC_API_KEY is not set. - [x] Manually trigger each failure mode once and confirm each produces a visible, specific failure state. *(all three run against a real local Postgres database and a running dev server, not just imagined — see the three sub-items below. `RESEND_API_KEY` was already absent from `.env`, so the send failure needed no setup; the other two were forced deliberately and reverted immediately after.)*

Reverted `pdf.ts` and confirmed a normal PDF renders again.
  - **Send failure:** called send with no `RESEND_API_KEY` configured — 502, `resend: RESEND_API_KEY is not set`, `send_failed` status/event. Root cause was the missing "un-fail" half of the state transition. *Fix:* a successful document generation from a `document_failed` state now restores the proposal to `approved`; `canSend` (and the button's "Retry send to client" label) now treat `document_failed` the same as `send_failed`. To avoid a different mistake — a render failure while merely previewing an unapproved draft wrongly implying the proposal was ever headed toward sending — the document route now only flips status into `document_failed` when the proposal was already `approved`, `document_failed`, or `send_failed`; a preview failure on an earlier-stage proposal (`draft`, `pending_review`, etc.) is still logged as a real failure event and still returns a clear error to the caller, it just doesn't lock the proposal out of normal editing. Verified the full cycle: force failure on an approved proposal → `document_failed` → fix and retry → back to `approved`, "Send to client" available again → send succeeds → `sent`.

## Suggested sequencing

Phases 0–1 are strictly sequential groundwork. Phase 2 depends on Phase 1's schema and intake endpoint existing. Phases 3 and 4 can overlap somewhat — the approval state machine (4) doesn't need the regeneration UI (3) finished, just the underlying section data from Phase 2 — but both should land before Phase 5, since Document Generation needs a stable, approved set of sections to render. Phase 6 depends on Phase 5 (there's nothing to email without a generated document) and on Phase 4's approval gate already being enforced. Phase 8 is a cross-cutting check best done once 1–6 exist, rather than perfected incrementally inside each phase — trying to fully solve failure handling per-phase tends to slow everything else down before there's anything working end-to-end to test failures against. Phase 10 starts now that both are done, since the testing evidence table asks for exactly that — Phase 7's and Phase 9's polish are already finished too, ahead of Phase 10's Loom walkthrough and demo link, as planned.
